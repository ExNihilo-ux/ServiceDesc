# Backend: ServiceDesc Airport Maintenance

Бэкенд системы автоматизированной обработки заявок на обслуживание аэропорта.  
**Стек:** FastAPI + asyncpg + PostgreSQL (pgvector) + Pydantic Settings v2 + Sentence Transformers.

## Роль в системе

Бэкенд выступает **интеллектуальным маршрутизатором**:
1.  Принимает заявки (текст, фото, геолокация) от мобильного приложения.
2.  Генерирует векторные эмбеддинги описаний неисправностей с помощью ML-моделей.
3.  Осуществляет семантический поиск исторических прецедентов через `pgvector`.
4.  Автоматически направляет задачи в профильные отделы на основе классификации ИИ.

## Архитектура приложения

Проект следует строгому разделению ответственности:

| Слой | Папка | Назначение |
| :--- | :--- | :--- |
| **API** | `app/api/v1/` | Роутеры FastAPI, модульная структура (`requests_main`, `requests_search`), общие зависимости |
| **Services** | `app/services/` | Бизнес-логика: ИИ-классификация, генерация эмбеддингов, обработка фото |
| **Repositories** | `app/repositories/` | Raw SQL + asyncpg. Фасад (`RequestRepository`) делегирует операции приватным реализациям в `impl/` |
| **Schemas** | `app/schemas/` | Доменные DTO (`requests/`), кастомные типы (`types.py`), Response DTO |
| **Settings** | `app/settings/` | Типизированная конфигурация (`database.py`, `app.py`). Чтение корневого `.env` |
| **Core** | `app/core/` | Инфраструктурные утилиты, фабрика `get_db_manager()` |
| **SQL** | `sql/migrations/` | Чистые SQL-скрипты схемы БД (SQL-First подход) |
| **Scripts** | `scripts/` | Утилиты для обучения моделей (`train_model.py`) и миграций |

### Ключевые технические решения

-   **Модульная структура API:** Эндпоинты разделены по функциональным блокам (CRUD, Search) для соблюдения SRP. Общие зависимости вынесены в `dependencies.py`.
-   **ИИ-сервис (AIService):** Использует модель `intfloat/multilingual-e5-large` (размерность 1024) для генерации семантических векторов. Поддерживает дообучение (fine-tuning) на данных аэропорта.
-   **Raw SQL вместо ORM:** Необходим для работы с типом `vector`, операторами косинусного сходства `<=>` и кастомными функциями поиска.
-   **Pydantic v2 Custom Types:** Логика nullable-полей вынесена в переиспользуемые `Annotated[BeforeValidator]` типы.
-   **Facade Pattern в репозиториях:** Публичный `RequestRepository` объединяет CRUD и Search операции, делегируя их приватным классам в `impl/`.
-   **Единый контракт ответов:** API возвращает типизированные `ResponseDTO`. Поля `out_*` полностью исключены.
-   **TDD по слоям:** Unit → Integration → E2E. Каждый уровень изолирован и имеет собственные фикстуры.

## ИИ-сервис и векторный поиск

Для семантического анализа заявок используется модель **Multilingual E5 Large**. Она позволяет находить исторические прецеденты по смыслу, а не только по ключевым словам.

### Workflow работы с моделями

1.  **Базовый режим:** Если папка `models/airport-finetuned` отсутствует, сервис использует базовую модель из HuggingFace.
2.  **Дообучение (Fine-tuning):**
    ```bash
    python scripts/train_model.py
    ```
    Скрипт обучает модель на парах «описание-категория» и сохраняет результат локально.
3.  **Использование:** После обучения `AIService` автоматически подхватывает улучшенную версию из папки `models/`.

## Стратегия тестирования (TDD)

Все тесты запускаются через `pytest` в режиме `asyncio_mode = "auto"`.

### 1. Unit-тесты (`tests/unit/`)
Проверяют чистую логику без БД и HTTP.
-   **Что тестируем:** Валидаторы эмбеддингов, бизнес-правила сервисов, семантику ML-моделей.
-   **Правило:** Обязательно передавать фейковые `DatabaseSettings` в конструктор. Не зависеть от `.env`.
-   **Запуск:** `pytest tests/unit/ -v`

### 2. Integration-тесты (`tests/integration/`)
Проверяют взаимодействие репозиториев с БД.
-   **Что тестируем:** SQL-функции, upsert-логику, векторный поиск, FK-констрейнты.
-   **Правило:** Каждая транзакция обёрнута в `BEGIN...ROLLBACK`. Результаты запросов проверяются как dataclass'ы.
-   **Запуск:** `pytest tests/integration/repositories/ -v`

### 3. E2E-тесты (`tests/e2e/`)
Проверяют полный HTTP-цикл через `httpx.AsyncClient`.
-   **Что тестируем:** Валидацию DTO, статус-коды, маппинг ответов, обработку ошибок.
-   **Правило:** Используется общая фикстура `client` с включенным `follow_redirects=True`. Пул БД подменяется через `app.dependency_overrides`.
-   **Запуск:** `pytest tests/e2e/ -v`

## Архитектура миграций (SQL-First)

Схема БД описывается чистым SQL. Alembic — только система версионирования и доставки.

### Структура папок

| Папка | Назначение |
| :--- | :--- |
| `sql/migrations/` | UP-скрипты (применение изменений схемы) |
| `sql/rollbacks/` | DOWN-скрипты (безопасный откат) |
| `alembic/versions/` | Python-обёртки (runner'ы), генерируются автоматически |
| `scripts/` | Утилита `new_migration.py` для создания тройки файлов |

### Workflow создания миграции

1.  **Создать новую миграцию:**
    ```bash
    python scripts/new_migration.py "add_hnsw_index_to_embeddings"
    ```
2.  **Написать SQL:** Заполни созданные `.sql` файлы кодом между `BEGIN;` и `COMMIT;`.
3.  **Применить:**
    ```bash
    docker compose exec backend alembic upgrade head
    ```
4.  **Откатить:**
    ```bash
    docker compose exec backend alembic downgrade -1
    ```

## ⚙️ Инфраструктура и запуск

-   **Python:** 3.14-slim
-   **DB:** PostgreSQL 16 + pgvector 0.7+
-   **ML:** Sentence Transformers (`intfloat/multilingual-e5-large`)
-   **Drivers:** `asyncpg` (runtime), `psycopg2-binary` (Alembic)
-   **Config:** Корневой `.env`, путь резолвится относительно модуля настроек
